## Goal and scope

Add explicit, root-scoped retention of successful scan history to support future
archive maintenance and limit growth from repeated full observation snapshots.
Include scan-summary inspection through API/CLI and opt-in cleanup of failed
scans outside the retained history window, as requested in the planning follow-up.
Prepare the design before implementation. Plan 005 remains reserved for archive
work. No automatic pruning or archive implementation is authorized here.

## Pre-implementation inspection

The current schema is version 2 in `src/archiver/catalog.py`. Foreign keys are
enabled on catalog connections. None of these relationships uses `ON DELETE
CASCADE`:

| Referencing column | Referenced row | Consequence for pruning |
| --- | --- | --- |
| `scan_runs.location_id` | `locations.id` | Scope candidates to one location; preserve locations. |
| `file_observations.scan_id` | `scan_runs.id` | Delete observations before their scan rows. |
| `locations.current_scan_id` | `scan_runs.id` | Never delete any location's current scan. |
| `file_observations.content_id` | `content.id` | Removing observations does not delete content. |
| `content_tag_assertions.content_id` | `content.id` | Assertions do not depend on scans or paths. |
| `content_tag_assertions.tag_id` | `tags.id` | Preserve tags and all assertion/retraction/provenance rows. |

Each successful scan stores a complete snapshot, not a delta chain.
`execute_current_scan()`, current-file and duplicate queries, exact path-tag
resolution, and reconciliation select observations through the current scan
pointer. They do not reconstruct inventory from old scans. Content queries
read the independent `content` table; content known only through removed scans
can remain known even with no remaining file observations. History iterators
join scans and observations and will naturally expose only retained history.

Existing observation indexes begin with `scan_id`, so child deletion can use
them. Candidate selection can filter `scan_runs.location_id/status` and order
by its integer primary key. No new index is justified for this minimal feature
without measurement. No schema migration, cascades, query rewrite, snapshot
compaction, or content garbage collection is needed.

One lifecycle detail needs a narrow addition: duplicate handles store a pinned
scan ID and load members later. They survive refresh today, but cannot load
deleted history after pruning. Current history/current-file/group/member
streams also hold SQLite cursors. Explicit maintenance must have a documented
stream-lifetime boundary, described below.

## Public API and result

```python
catalog.prune_history(root, keep_last=3, dry_run=True)
catalog.prune_history(root, keep_last=3, dry_run=False)
catalog.prune_history(root, keep_last=3, include_failed=True, dry_run=True)
```

Add `Catalog.prune_history(root: Path, *, keep_last: int = 3,
dry_run: bool = True, include_failed: bool = False) -> PruneHistorySummary` and an immutable typed summary
exported from `archiver`. Proposed fields:

- `root: Path`: canonical root.
- `keep_last: int`, `dry_run: bool`, `include_failed: bool`: effective request.
- `successful_scans_retained: int`: successful scans remaining after the
  proposed/applied operation.
- `oldest_retained_scan_id: int | None`: the transaction's failure-cleanup cutoff,
  avoiding a separate potentially stale CLI lookup.
- `scans_to_remove: int`, `observations_to_remove: int`: exact rows selected;
  in applied mode these are the rows actually removed in that transaction.
- `successful_scans_to_remove: int`, `failed_scans_to_remove: int`: breakdown
  of the total scan count, making opt-in failure cleanup explicit in previews.

Do not return an unbounded tuple of scan IDs. Document that a dry-run result is
a report, not an applicable deletion token or a promise about a later call.

Validate eagerly: `keep_last` must be an exact `int` in `1..2**63-1`, rejecting
bool/non-integers with `TypeError` and out-of-range values with `ValueError`.
Require actual bools for `dry_run` and `include_failed`. Validation precedes catalog reads.
Use existing root canonicalization and symlink rejection; this first version
requires an accessible directory, as the other root-scoped APIs do. Maintenance
of disconnected/missing roots is deferred. An existing but unknown/unscanned
root returns zero counts without creating a location or scanning anything.

## Scan summaries and CLI

Existing capabilities: `scan_history()` yields all scan IDs, locations, statuses,
and timestamps; `observation_history()` yields the recorded file observations.
`current_scan(root)` and `current_summary(root)` describe the current inventory.
CLI `catalog info ROOT` shows that one current scan. There is currently no
historical per-scan count/size summary API or history-listing CLI command.

Add `scan_summaries(root: Path) -> Iterator[ScanHistorySummary]`, newest scan ID
first, without changing existing history methods. Each immutable summary has
`scan: ScanRun`, `files_observed: int`, `total_bytes_observed: int`, and
`is_current: bool`. `ScanRun` already supplies ID, root, status, started time,
and optional completion time. Include completed, failed, and running scans.
Use a single root-scoped aggregate query with a left join from scans to
observations so empty scans appear with zero files/bytes. Count
`file_observations.id`, not `COUNT(*)`, which counts the empty left-join row;
use `COALESCE(SUM(size_bytes), 0)`. Totals include every physical file observation,
including duplicate copies, rather than distinct-content bytes. Group by scan
identity and derive `is_current` from the same query's location pointer.
Avoid per-scan queries
or materializing all file observations in Python. Unknown/unscanned roots yield
no rows. Resolve the root/current pointer and execute reads on first advancement,
consistent with existing streaming history methods. The iterator requires the
catalog open and closes its cursor on exhaustion, explicit close, or error.
It reports one SELECT's observed history, not a reusable pinned paging session.

Add `archiver catalog history ROOT [--limit N]`, defaulting to 20 newest scans
with a positive validated limit. Show scan ID, UTC start/completion date-time,
status, current marker, observed file count, and human-readable total bytes.
Missing completion time is displayed as absent. Failed/running totals describe
only persisted observations and must be labeled partial, not complete inventory.
Normal refresh failures currently roll back without creating failed scan rows;
listing/cleanup must still support existing or manually seeded failed rows.
The CLI must explicitly close the summary iterator after reaching its limit;
do not rely on `break` or garbage collection. There is no new all-history
materialization, pagination, total-history reduction, or generic query facade.
Use existing byte formatting and timestamp conventions, but explicitly label
UTC and distinguish absent completion times from zero timestamps. Seed fixed
timestamps in tests; no local-timezone or wall-clock assumptions.

Add `archiver catalog prune-history ROOT [--keep-last N] [--include-failed]
[--apply]`. Default is a write-free preview with `keep_last=3`; only `--apply`
requests deletion. Print retention and candidate scan/observation counts with
the successful/failed breakdown. Forward to the same API policy and transaction
implementation. No generic `--force` flag: no option bypasses minimum retention,
current-pointer protection, foreign keys, rollback, or running-scan protection.
CLI invalid arguments fail before opening the catalog. These commands do not
scan or hash source files, and history inspection is read-only.
Both new commands require an existing catalog; do not initialize or migrate it
implicitly. Apply the API's `1..2**63-1` bound to CLI `--keep-last`, and the same
positive range to `--limit`, before catalog opening. Missing/invalid catalogs
and operational errors return 1 on stderr; invalid syntax/options return
argparse exit code 2. Add `HistoryPruningError` to the CLI's handled errors.
Handle SQLite inspection errors within the new history command using the
existing CLI error convention, without changing unrelated read-API exceptions.
Print successful pruning output only after commit; previews explicitly say
that no changes were written. Unknown/unscanned roots have an explicit empty
history or zero-candidate report, never a misleading inventory scan.

## Retention policy and invariants

- Successful means `scan_runs.status = 'completed'`. Keep up to N of the most
  recent successful scans for this location by descending scan ID, consistent
  with serialized scan creation and deterministic history ordering. Do not rank
  by wall-clock timestamps, which can tie or move backward.
- By default remove only older completed scans and their observations. Failed
  rows remain useful diagnostics and do not count toward N.
- With `include_failed=True`, also delete failed scans whose IDs precede the
  oldest retained successful scan. This applies the same retained-history
  window to failure diagnostics. Newer failures within that window are retained;
  with no successful scan there is no cutoff and no failed rows are removed.
  Reports and help must state this boundary; the option does not delete every
  failed row irrespective of age. Arbitrary failed-scan deletion is deferred.
- Running scans are never deleted, even if apparently stale. Determining whether
  a running scan is abandoned requires a separate recovery policy.
- N is at least 1. If fewer than N successful scans exist, keep all of them;
  explicitly included failed scans before that retained window may still be
  removed. Empty successful scans count toward retention.
- Never delete a scan referenced by any `locations.current_scan_id`, including
  unexpected cross-location references. If the proposed set includes such a
  scan, reject the operation with a clear error rather than changing pointers
  or silently retaining a different number of scans. Keep foreign keys enabled.
- Preserve every `content`, `tags`, and `content_tag_assertions` row byte for
  byte, including content seen only in pruned history, retracted assertions,
  and provenance. Preserve other locations and all retained scan/observation IDs.
- No scan-ID renumbering. Keeping the highest successful ID and deleting failed
  rows only before the retained window avoids deleting the maximum scan row ID, which also
  prevents SQLite's ordinary row-ID allocation from reusing pruned scan IDs.
- Preserve invariants 1–7, 9, 15–22. Invariant 8 still applies to retained
  records: explicit user-requested retention removes old observations but never
  conflates or rewrites the identities of scans that remain. Retention does not
  remove tag history. Add a dated explanation of this explicit maintenance
  policy to the domain/invariants documentation at implementation, preserving
  the invariant that retained observations identify distinct scans.

Concrete cutoff example (IDs increase left to right):

```text
ID       1       2          3       4          5        6       7          8
status   failed  completed  failed  completed  running  failed  completed  failed
```

With `keep_last=2`, retain successful scans 7 and 4. Default candidates are just
scan 2; `include_failed=True` adds failed scans 1 and 3 (IDs below cutoff 4).
Failed scans 6/8 and running scan 5 stay intact. With `keep_last=3` or a larger
value, only failed scan 1 is eligible with opt-in cleanup (cutoff 2). With no
successful scans there is no cutoff and no deletion, even with opt-in cleanup.
Report the cutoff as the oldest retained successful scan ID in the CLI explanation
when failed cleanup is requested, including an explicit no-cutoff explanation.

## Simplest safe transaction

1. Reject entry with an already-active connection transaction using a clear
   `HistoryPruningError`; do not commit or roll back someone else's work.
   Make this check after eager argument validation but before beginning any
   transaction or doing database-dependent work, including for unknown roots.
2. For dry run, use one short read transaction to select the location, inspect
   current pointers, and count retained/candidate scans and observations from
   one consistent snapshot. End the read transaction without writes, temp-table
   writes, or a reserved writer lock.
3. For application, start `BEGIN IMMEDIATE` before resolving the location and
   selecting candidates. Concurrent refresh/tag writers serialize or fail with
   SQLite's existing timeout policy; no count/delete race is introduced.
4. Use a shared private candidate predicate/CTE scoped to this location: completed
   scans excluding its newest N, plus opt-in failed rows before the oldest
   retained successful scan. Check current-pointer references and
   count candidate rows before deleting anything.
5. Delete `file_observations` selected by candidate scan ID, then `scan_runs`.
   Reuse the same SQL selection inside the transaction rather than collecting
   all scan or observation IDs in Python or expanding SQLite parameter lists.
   Candidate selection remains stable after child deletion because it depends
   on scan rows. Verify affected-row counts against the report. For CTE-prefixed
   DELETEs Python sqlite3 can report `cursor.rowcount == -1`; use `SELECT changes()`
   immediately after each DELETE on this connection, before another mutation,
   instead of interpreting -1 as an affected-row count.
6. Commit only after both deletions succeed. Roll back on SQL/validation errors
   and interruption, including `KeyboardInterrupt`; close every cursor. Wrap
   operational pruning failures in exported `HistoryPruningError` with the
   original cause, while preserving validation errors and interruption types.
   Track whether this operation successfully began a transaction: a failed
   `BEGIN IMMEDIATE` must not roll back an unrelated transaction, and a failed
   commit must still trigger rollback of this operation's uncommitted changes.
   End dry-run read transactions on success and on every failure path as well.

Share reporting/selection helpers between dry-run and applied paths. A later
applied call always recomputes its own candidate set. No reconciliation baseline
or scan application semantics change: a change set based on the preserved
current scan remains valid unless another refresh changes that baseline.

## Stream and handle lifetime

Pruning is an explicit maintenance boundary. Callers must finish or close open
history/summary/file/group/member iterators before applied pruning and must not consume
them concurrently with pruning on this or another connection. Do not add a
global stream registry, reader pinning, or automatic retention extension.
Dry runs do not invalidate readers. Normal refresh retains existing lifetimes.

Materialized values remain usable after pruning. A duplicate handle for a
retained scan continues to load its original members. For a deleted scan, add
a narrow existence/status check at member-stream execution and raise exported
`PrunedScanError` rather than silently reporting an empty group with stale
nonzero counts. Test this after closing the outer iterator while the originating
catalog remains open. Existing handles remain bound to that catalog and do not
reattach to a reopened connection; keep existing closed-catalog failure behavior.
Test persisted retention separately after reopening the database. Document that
arbitrary overlapping maintenance/iteration is outside the supported lifecycle;
do not promise snapshot isolation for
interleaved cursors on the same SQLite connection.

This requires small lifecycle guards and documentation amendments, not a
refactor of current-state queries or the historical data model. Preserve the
existing refresh pinning guarantee explicitly; only deliberate history deletion
invalidates handles for removed scans.
Validate a handle's scan against its location and completed status, and perform
the check when its member iterator first advances, not when the generator is
constructed. A closed catalog must keep its existing closed-connection error;
do not misclassify operational SQLite failures as `PrunedScanError`.

## Maintenance scope and documentation

Do not invoke pruning from scanning, reconciliation, opening, or closing.
No scheduling, archive ingestion, content deletion, arbitrary failed/running cleanup,
schema/index change, or new dependency is included. `VACUUM` stays a separate,
optional SQLite maintenance action; do not call it or add a vacuum API here.
Deleting history makes pages available for SQLite reuse; do not promise a
smaller database file or a permanent size bound while preserving all content.

Update `docs/catalog-api.md` with the exact signature, result/error types, and
examples; update exports/public API tests and query/stream lifecycle docs.
Update CLI reference/help and examples for history listing and preview/application,
including partial failed-scan totals and the failed-cleanup cutoff.
Expected code boundaries: orchestration and transaction ownership in
`catalog.py`; narrow history-summary SELECT/row materialization in
`_sqlite_query.py`, alongside existing history reads; immutable result types in
`models.py`; errors in `errors.py`; public exports in `__init__.py`; CLI parsing
and rendering in `cli.py`. Keep shared pruning selection SQL private and avoid
extending the public query grammar or changing existing history signatures.
The exact-signature gate in `tests/unit/test_public_api_contract.py` requires
updating `docs/catalog-api.md` together with both new methods. Add import/export
checks for `ScanHistorySummary`, `PruneHistorySummary`, `HistoryPruningError`,
and `PrunedScanError`. Existing CLI help/contract coverage must include the two
new subcommands without changing old command defaults.
Add a dated parent-plan cross-reference and retention explanation without
