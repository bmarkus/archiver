## Goal and boundary

Compare the known current content of an explicit source catalog/root with an
explicit target catalog/root. Return complete summary counts and bounded batches
of distinct source identities, identifying those not represented at the target.
Make those batches suitable for constructing the temporary sync workspace in
005.3–005.4 without collecting entire catalogs or a copy manifest in Python.

This child is read-only. It does not create the persistent operation workspace,
write a manifest, copy files, register target observations, mark source tags,
publish snapshots, or implement Archiver. It prepares the comparison boundary
used by those later operations. Writing this draft does not activate any plan.

## Existing code and invariants

- Catalog schema 3 records catalog UUIDs, content `(algorithm, digest)`, locations,
  successful snapshots, origin, and path observations. `locations.current_scan_id`
  selects the current inventory; it may originate from a full scan or targeted
  update. Reuse `ContentId`, `Location`, and opaque `InventoryRevision` semantics.
- `Catalog.contents()` includes identities with no current paths and is not a
  suitable set of physically represented current content. `files(root)` is
  scoped correctly but its ordinary ordering and records do not directly provide
  a database-side cross-catalog distinct-content comparison. Do not replace SQL
  comparison with Python sets or repeatedly query once per source identity.
- Existing indexes cover `(algorithm, digest)`, snapshot/path lookup, and content
  observation lookup. Evaluate the query using these indexes first. No schema
  version bump or persistent index change is planned without demonstrated need.
- Root validation currently requires accessible directories. Keep that contract;
  comparing offline/missing roots is outside this child. Root/path metadata is
  only scope information, never content identity.
- Invariants 1–4 and 6 govern identity; 7–9 govern committed snapshot scope;
  10–11 mean comparison grants no mutation authority; 15–20 require preserved
  metadata, explicit versions, read-only failure, and truthful partial outcomes;
  21 requires explicit deterministic ordering. No authoritative-document amendment
  is needed for this read-only operation. Report any newly discovered conflict
  before changing the design.

## Comparison semantics

Let S and T be distinct identities represented by file observations in the
captured successful source and target snapshots respectively.

- Missing source content is `S minus T`; represented source content is their
  intersection. Target-only content is `T minus S` and is summarized, not emitted
  as proposed source work.
- Compare the full algorithm and digest, never local integer content IDs, path,
  filename, size alone, or abbreviated hashes. One identity with many paths counts
  once. Empty files are ordinary content.
- Content known only in historical snapshots or the independent `content` table
  is absent from the corresponding current set. Other roots do not contribute.
- Existing but unregistered/unscanned roots have an empty known set and a revision
  with no snapshot. Scope metadata explicitly distinguishes this from an observed
  empty successful snapshot; do not create locations/scans as a side effect.
- Same catalog/same root yields no missing content. Different roots in one catalog
  are supported and compared independently. Reverse direction may produce a
  different result. Do not reject valid comparisons merely because two Catalog
  objects refer to the same database.
- Cataloged presence is not proof that a physical target instance still exists.
  Do not scan, hash, open, or stat individual cataloged files to improve the result.
  Copied destination bytes must still be freshly verified in 005.4.
- For each source identity, select the lexicographically smallest full POSIX
  relative path using SQLite BINARY ordering as a deterministic representative.
  Return its cached mtime and expected size, plus the source instance count.
  This is a candidate source path, not a verified available file or an instruction
  to delete its duplicates. Alternate-path fallback is deferred to 005.4.
- Detect contradictory sizes for the same identity across the compared current
  sets, or disagreement between scoped observations and their content size, and
  fail clearly. Size is a consistency check, not an extra identity component.
- Validate observation references and identities in both captured inventories
  before exposing results, including target-only and already-present content.
  Invalid records must fail clearly rather than disappear through an inner join.
  Keep `ContentId`'s existing SHA-256-only validation.

## Planned public API

Use the names below and a small comparison session rather than extending the
general query grammar with database joins. The Catalog entry point is
`compare_content(self, target: Catalog, *, source_root: Path, target_root: Path)
-> ContentComparison`:

```python
with source.compare_content(
    target,
    source_root=source_root,
    target_root=target_root,
) as comparison:
    print(comparison.summary())
    # A future workspace writer consumes each batch without retaining older ones.
    for batch in comparison.batches(batch_size=1000):
        for row in batch:
            print(row.content_id, row.source_relative_path)
```

The example is a small-data illustration; future manifest construction writes
rows to its own workspace rather than printing every entry. It does not execute
copies or register the returned source observations in the target.

Export these types and the comparison error from `archiver`:

- `ContentComparison`: a single-use context-managed session with source/target
  scope metadata as `source_scope` and `target_scope`,
  `summary() -> ContentComparisonSummary`, `batches(...)`, and `close() -> None`.
- `ComparisonScope`: catalog UUID, canonical root, `Location`, opaque inventory
  revision, and `has_inventory` flag. Capture it from the dedicated comparison
  connection, not by sampling live current queries again. Retain the existing
  `Location` type; its ID is catalog-local metadata. Use the opaque revision for
  baseline checks, never a location or snapshot ID alone.
- `ComparedContent`: `content_id: ContentId`, `size_bytes: int`,
  `source_relative_path: PurePosixPath`, `source_mtime_ns: int`,
  `source_instance_count: int`, and `in_target: bool`. No destination path,
  execution status, or trusted destination observation is inferred.
- `ContentComparisonSummary`: integer fields `source_content_count`,
  `target_content_count`, `shared_content_count`, `missing_source_content_count`,
  `target_only_content_count`, and `bytes_to_copy`.
  Unique bytes sum one expected size per missing identity, not all duplicate
  instances; this is an estimate of copy bytes, not actual free-space demand.
- `ContentComparisonError`: a public error for catalog validation, attachment,
  inconsistent scoped records, SQL reads, and session-lifetime failures, preserving
  the underlying exception. Argument validation uses `TypeError`/`ValueError`.

`batches(*, batch_size: int = 1000, include_present: bool = False)` yields bounded
immutable tuples ordered by full `(algorithm, digest)` ascending. By default it
emits only missing content. `include_present=True` emits one classified row for
every source identity so a workspace can record already-represented skips without
tagging the source. The representative uses a separate explicit path ordering.

Reject bool/non-integer batch sizes, values outside `1..2**63-1`, non-bool
`include_present`, and invalid root/target argument types eagerly. A batch size
is a maximum, not a promise to allocate that much memory in advance. No global
unbounded `fetch()`/`list()` materialization is introduced. The comparison batch
default is not the final copy batch size; 005.4 chooses that separately.

Summary and batches describe the same captured snapshots. Summary can be read
repeatedly; repeated sequential batch traversals use those same snapshots.
Allow only one active batch iterator per session; reject overlapping traversals
clearly. Batch iterators expose `close()`: closing or exhausting one releases its
cursor while keeping the session's captured snapshots available for another
traversal. After breaking a loop, explicitly close the iterator or leave the
session context; a plain `break` does not guarantee cleanup. Context exit closes
even an abandoned iterator. Reads before entry or after close fail clearly;
normal close is idempotent, and a closed session cannot be reopened.

## SQLite design and consistent reads

### Dedicated read-only comparison connection

Prefer a dedicated SQLite connection with an in-memory main database and fixed
source/target aliases attached using bound, correctly encoded file URI values
with `mode=ro`. Enable `uri=True`, foreign-key enforcement, and
`PRAGMA query_only=ON` before starting the read transaction. Foreign-key
enforcement does not replace validation of existing scoped records.
Do not use `immutable=1`: catalogs may legitimately publish new snapshots while
comparison is open. Never attach either input in writable/create mode, change
journal mode, run migrations, or mutate the Catalog objects' existing connections.

Reuse one attachment when both endpoints resolve to the same physical database;
otherwise attach each separately. Detect file identity using existing paths and
filesystem metadata where appropriate, not catalog UUID alone (a copied database
can share a UUID). Fixed aliases and bound values avoid SQL interpolation of
caller paths. Test filenames containing spaces, non-ASCII, `#`, and `?` where
supported. An absent input must fail without creating a database file.

Before opening the comparison, require both Catalog handles to be open and not
inside caller-owned transactions; reject pending work without changing it.
Validate supported schema/required fields and UUIDs on the attached inputs,
reusing narrow validation helpers where possible. Verify that inputs correspond
to the supplied Catalog handles using UUIDs and available filesystem identity
checks during session opening; fail on detected replacement. This is an opening
check, not protection against every concurrent file replacement, including a
same-UUID copy substituted before those checks. Separate copied catalogs remain
valid inputs and are not deduplicated by UUID.
Keep URI/version logic internal; no general public ATTACH API is needed.

### Snapshot capture and lifetime

After attaching and configuring the read-only connection, explicitly begin a read
transaction. Resolve each root and its current successful snapshot in this read
scope, validating pointer/location/status consistency. Empty known sets are valid;
a corrupt or dangling non-null current pointer is not an empty set.

Read/capture both inputs before exposing the session's summary or batches. Scope
all subsequent SQL to those captured IDs, never a newly resolved current pointer.
Attached databases can establish their snapshots at different first reads: this
is a stable pair of independently captured inventories, not a claim that two
independent catalogs were observed at one globally atomic wall-clock instant.

Concurrent refresh or pruning must never mix revisions in the session. Under WAL,
the read transaction can preserve its earlier view; under rollback journaling,
writers may wait/fail busy while readers remain open. Document this limit and
honor SQLite's ordinary bounded timeout; introduce no retry daemon or indefinite
wait. If a consistent read cannot be maintained, fail rather than switching to
newer rows or treating missing history as missing content.

Session close/context exit, validation/read failure, or interruption closes the
active cursor, transaction, and dedicated connection. Iterator close/exhaustion
alone releases only its cursor, as described above. Do not close caller-owned
Catalog handles or change their transaction state. The returned immutable scope,
summary, and batch values remain ordinary captured data after close; SQL-backed
methods do not. A new session captures new inventories.

Read-only describes intentional application writes: SQLite-managed WAL/SHM/lock
activity may depend on filesystem/journal mode. Do not promise byte-identical
sidecars during concurrent writers. Isolated read-only tests must verify unchanged
catalog logical contents and main database bytes, with no source-file mutation.

## SQL execution and bounded memory

Use scoped source/target observation relations joined to their own content tables.
Group source instances by full identity and choose the representative in SQL.
Use a SQL semi/anti-join (for example `EXISTS`/`NOT EXISTS`) against distinct current
target content, matching algorithm/digest across databases. Local integer IDs are
only join keys within their own database. Do not loop over identities in Python
to perform target lookups.

Compute complete aggregate counts/bytes in SQL, without adding batch limits to
the summary. Stream ordered result rows with `fetchmany(batch_size)` or an
equivalent bounded fetch. SQL may use temporary sorting/grouping storage; bounded
Python memory does not imply bounded total SQLite sorting space or constant-time
startup. Do not copy both entire catalogs into a new database to compare them.

Inspect representative `EXPLAIN QUERY PLAN` output, including a large duplicate
group and mostly distinct inventories, and ensure snapshot scoping uses existing
indexes where practical. Prefer a grouped current-target relation if a correlated
join otherwise repeatedly scans all target observations. Avoid brittle tests
asserting an exact SQLite plan or machine-specific speed. Add a persistent index
only after measuring and recording a necessary explicit schema-plan amendment.

## Handoff to the temporary sync workspace

005.2 yields identities, candidate source observations, counts, and captured scope
tokens. A later 005.3–005.4 writer consumes these batches into its own operation-
scoped workspace. Workspace rows distinguish candidates/already-represented
content from actual verified destination success. They are not Catalog records.

The later writer must mark manifest construction complete only after exhausting
comparison successfully and recording its scope metadata. Interrupted comparison
or workspace insertion must not produce a ready copy plan. This child exposes
clear failure/exhaustion behavior; it does not implement that durable ready flag.
No schema or workspace-version contract is imposed before 005.3 specifies it.

Close comparison readers once manifest construction finishes, before any physical
copying, target publication, or retention. The workspace may outlive the read
session but receives no ongoing lock or guarantee of freshness. Later execution
revalidates source/target revisions and physical conditions. Compare-time presence
does not replace destination verification. Do not reconstruct the opaque revision
by passing around naked scan IDs; any durable revision encoding is 005.3 work.

Bounded comparison batches do not publish target inventory. 005.4 still requires
one final publication of verified successful entries, with a separate bounded-
memory ingestion boundary because 005.1's preparation API materializes its input.
This child neither changes 005.1 nor begins that execution/publication work.

## Schema, authority, and non-goals

No persistent schema changes, migrations, managed-storage authority, target
snapshots, tags, or operation summaries are introduced. Reuse schema-3 validation;
reject legacy/unsupported versions without writes and preserve rebuild guidance.

No physical file verification/copy/deletion, destination collision policy,
bidirectional synchronization, catalog merge, all-root comparison, alternate
source-path fallback, permanent cache, user-supplied query grammar joins, CLI
commands, workspace lifecycle/execution implementation, receipt mechanism,
automatic pruning, or Rust. No new dependency is expected; use sqlite3.

## Acceptance tests

1. Overlap and both directions: small S/T fixtures verify exact identity rows,
   presence classification, distinct counts, target-only count, and unique bytes.
   Seed unrelated local content IDs so integer-ID comparison would fail.
2. Duplicate/empty/nested content: many source and target copies yield one source
   row per identity, correct instance counts, deterministic representative path
   and mtime, and empty-file handling. Use directories beside similarly named
   files to distinguish BINARY representative ordering from scan component order.
3. Scope/history: other roots, historical-only identities, known content with no
   current paths, full/targeted origins, and retired instances do not contaminate
   either current set. Existing unscanned roots and successful empty snapshots
   have correct empty sets and distinguishable scope metadata.
4. Same input: same root/same Catalog, separate handles to one database, different
   roots in one database, and separate copied catalogs with equal UUIDs work
   according to their actual inventories, without duplicate attachment errors.
5. Stale filesystem: modifying/removing physical source/target files after scanning
   does not silently change comparison results. Patch scan/hash/file-opening
   boundaries to reject any attempted refresh/verification; root validation and
   SQLite input access are still allowed.
6. Batches and memory: results spanning many batches have no omissions/repeats,
   no tuple exceeds the requested bound, full summaries ignore batch size, and
   `include_present` preserves ordering/classification. Exercise one very large
   duplicate group without materializing its members in Python. Instrument the
   read boundary to reject unbounded result fetches and per-identity target SQL;
   do not rely on wall-clock or brittle absolute-memory thresholds.
7. Session consistency: deterministic independent-connection WAL refresh/pruning
   during summary/batch consumption preserves the old scoped view or fails clearly,
   never mixes old/new rows. New sessions see committed successors. Rollback-mode
   contention releases locks on closure; use explicit synchronization/zero timeout
   fixtures rather than timing-dependent sleeps.
8. Lifetime/failure: iterator close/exhaustion permits sequential replay; an early
   break followed by explicit iterator close or session exit releases the expected
   resources. Overlapping traversals and use before entry/after close fail clearly.
   SQL failure after a batch and interruption close the session's resources.
   Later caller Catalog operations work; pending caller
   transactions are rejected without commit/rollback or loss of pending work.
9. Input/catalog validation: invalid types/options/batch sizes, unavailable roots,
   missing/replaced databases, unsupported/legacy versions, malformed required
   schema/current pointers, orphaned observations, invalid identities, and
   contradictory sizes fail clearly without writes. Cover invalid target-only
   and already-present records as well as emitted missing-source records.
   URI-special filenames work on supported platforms; nonexistent files are not
   created. Bind values rather than interpolating aliases/paths.
10. Read-only guarantees: input logical dumps and main database bytes remain
    unchanged in isolated success/failure tests; physical source/target bytes,
    mtime, and mode remain unchanged. Demonstrate readonly attachment/query-only
    protection. No scan, tag, location, operation, or snapshot rows are created.
11. Workspace-oriented integration: a test-only SQLite sink consumes several
    batches and scope/summary values into scratch rows; source/target remain
    unchanged, represented rows are classified rather than copied candidates,
    and a deliberately interrupted sink never reports a complete build. Do not
    introduce a production workspace schema or copy engine to satisfy this test.
12. Persistence/regression: comparisons after Catalog close/reopen agree with
    captured inventories; all existing query/stream/retention/public API tests
    pass. Document the new API, error, type exports, representative policy,
    non-global snapshot guarantee, and memory/locking limits.

All tests use temporary catalogs/directories, deterministic fixtures/failure
injection, and no network, user archives, or machine-specific paths. Each behavior
above needs automated coverage where practical. Public examples use small data
and close comparison contexts before any later Catalog mutation.

## Implementation outcome — 2026-11-12

The user explicitly activated 005.2 after review. This completion record
supersedes the draft-only status in the historical planning notes above.

Implemented `Catalog.compare_content()` and exported `ContentComparison`,
`ComparisonScope`, `ComparedContent`, `ContentComparisonSummary`, and
`ContentComparisonError`. A dedicated in-memory connection attaches inputs with
encoded, bound readonly URIs, enables foreign keys and query-only protection,
and captures both inventories in one explicit read transaction. Same physical
databases share an attachment; copied catalogs are not deduplicated by UUID.
Attached schema/version/UUID and scoped record validation precedes results.

SQL groups current identities, selects BINARY-ordered representatives, joins
target identities, and computes complete summaries. No per-identity target
queries or whole-inventory Python materialization are used. Existing query-plan
indexes support snapshot-scoped observation reads and representative lookup;
grouping uses SQLite temporary storage. No persistent index or schema change
was necessary. Batch iterators are primed internally so explicit close works
even before their first public read. Iterator closure preserves session snapshots;
session closure/failure releases all dedicated resources and leaves caller handles
untouched.
