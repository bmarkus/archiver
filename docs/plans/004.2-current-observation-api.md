## Goal

Expose the first public, typed query grammar for current file observations while preserving the existing bounded current-file search contract.

Plan 004.1 established an internal description/compiler/executor seam. This subplan adds a small usable public API over that seam: a semantic source, typed path and ordering expressions, immutable transformations, and one bounded materialization operation.

The target API is:

```python
from archiver.query import mtime, path, size

query = catalog.files(root).where(path.glob("nested/*.txt")).sort(size.desc()).limit(10)

rows = query.fetch()
```

## Public API

Add:

```python
Catalog.files(root: Path) -> CurrentFileQuery
```

`CurrentFileQuery` is immutable, lazy, and bound to the `Catalog` that created it. It exposes only:

```python
query.where(predicate)
query.sort(order)
query.limit(count)
query.fetch()
```

Add a public `archiver.query` module containing the query type and the initial field vocabulary:

```python
path.glob(pattern)
path.asc()
path.desc()

size.asc()
size.desc()

mtime.asc()
mtime.desc()
```

Export `CurrentFileQuery` from the top-level `archiver` package for type annotations. Keep `path`, `size`, `mtime`, and their concrete expression types in `archiver.query` so field names do not crowd the top-level namespace.

Field, predicate, ordering, and query values are frozen typed objects. They contain semantic field tokens, never SQL column names, SQL fragments, or executable callbacks.

## Query semantics

- `Catalog.files(root)` validates and canonicalizes the filesystem root when the query is constructed but does not resolve a current scan or execute observation SQL.
- A new query defaults to relative-path ascending order and a row limit of 20.
- `where()` accepts only the current-file predicate types approved here and accumulates repeated predicates using logical AND.
- `sort()` accepts one typed ordering expression and replaces the previous ordering.
- `limit()` replaces the previous row bound and requires a positive integer.
- Clause meaning is independent of method-call order: predicates apply before ordering, and ordering applies before limiting.
- `fetch()` returns `tuple[FileObservation, ...]` and leaves the query reusable.
- Fetch resolves the root's persisted location and latest successful scan at execution time. A query constructed before its first successful scan can therefore return rows after that scan.
- A valid but unknown or not-yet-scanned root returns an empty tuple.
- Fetch after catalog closure fails through the existing SQLite connection lifecycle; it does not reopen the catalog implicitly.
- No public unbounded materialization is introduced. Existing `Catalog.current_files()` retains its current unbounded compatibility behavior.

Path matching remains a case-sensitive SQLite GLOB over the complete POSIX relative path. Empty and otherwise valid string patterns keep SQLite's existing matching behavior.

Ordering semantics are explicit:

- the default is `path.asc()`;
- callers choose direction explicitly for size or observed mtime;
- relative path ascending is the deterministic tie-breaker for size and mtime;
- full relative path is used for ordering, never a truncated display value.

`mtime` means the observed filesystem modification time stored as `mtime_ns`; it is not scan time or content identity.

## Internal design

### Bound query and semantic description

`CurrentFileQuery` stores the canonical root, immutable transformations, and a private binding to its catalog. The binding is excluded from its public representation and value comparison. The public object exposes no SQLite connection, cursor, SQL statement, or schema name; its private catalog binding is used only when a terminal operation executes.

At `fetch()` time, the catalog resolves the current persisted `Location`. If none exists, it returns an empty tuple. Otherwise it constructs the internal `CurrentObservationQuery` introduced in 004.1 with the query's predicates, ordering, and limit, then delegates to the SQLite executor.

This preserves lazy current-state behavior without weakening the 004.1 rule that an executable internal description requires a persisted location.

Immutable transformation rules are:

- `where()` returns a replacement query with the predicate appended to a tuple;
- `sort()` returns a replacement query with one new ordering expression;
- `limit()` returns a replacement query with one new positive bound;
- no method mutates its receiver.

### Expression vocabulary

Use a closed semantic field token for path, size, and mtime. Field objects create only the valid expressions for their type:

- the path field creates GLOB predicates and ascending/descending orders;
- size and mtime create ascending/descending orders;
- arbitrary `Field` construction is not required as public API in this subplan.

The public query validates expression types before reaching compilation. Unsupported or manually forged expressions fail clearly rather than being interpreted optimistically.

### SQLite compilation and execution

Extend the 004.1 compiler to:

- map closed field tokens to trusted SQL expressions;
- compile each path predicate as `observations.relative_path GLOB ?`;
- combine predicates using `AND`;
- compile the selected primary order plus the relative-path tie-breaker;
- append `LIMIT ?` for the mandatory public bound;
- bind patterns, location ID, and limit as parameters rather than interpolating them.

The 004.1 `Catalog.current_files()` path continues to construct an unbounded internal description with path-ascending ordering. Public unbounded fetching remains unavailable.

### Existing bounded search

Refactor the row-selection portion of `Catalog.search_current_files()` to compose the new grammar, including translation of its `path_glob`, `sort_by`, `reverse`, and `limit` arguments.

Its complete match-count and total-size calculation may remain a focused existing aggregate query in this subplan. Plan 004.3 will move reductions onto the grammar. Avoid duplicating row filtering, ordering, or limiting SQL between `search_current_files()` and the compiler.

The mapping is exact:

- `sort_by="path"` maps to path ascending, reversed when requested;
- `sort_by="size"` maps to size descending, reversed when requested;
- `sort_by="date"` maps to mtime descending, reversed when requested.

## Acceptance criteria

- `Catalog.files(root)` returns the documented immutable bound query.
- The public grammar supports only path GLOB filtering, path/size/mtime ordering, positive row limits, and bounded `fetch()`.
- Default and explicit bounds are applied by SQLite before observations are materialized.
- The compiler receives typed semantic expressions and maps them through a closed field vocabulary; public input cannot inject SQL identifiers or fragments.
- `search_current_files()` uses the grammar for row selection while preserving its result type, complete totals, and behavior.
- `current_files()`, tag-aware searches, history APIs, and CLI behavior remain compatible.
- The focused public notebook executes successfully and contains no private query/compiler imports.
- No schema, tag, duplicate, historical-query, projection, or public unbounded-materialization behavior is introduced.
- Required validation results and implementation decisions are recorded in this plan.

## Non-goals

Exclude:

- content-identity, size-comparison, mtime-comparison, or tag predicates;
- OR/NOT predicate composition;
- arbitrary caller-created field names, raw SQL, or Python callback predicates;
- projection or selection;
- count, total-size, first-result, existence, or streaming terminals;
- public unbounded collection;
- grouping, aggregation, and duplicate queries;
- historical-observation grammar;
- migration of tag-aware current-file search;
- CLI query construction changes;
- removal, renaming, or deprecation of existing APIs;
- schema/index changes, caching, snapshots, async execution, or alternate SQL backends;
- source-file mutation, archive management, ingest, merge policy, working copies, remote storage, GUI behavior, background watchers, or Rust.
