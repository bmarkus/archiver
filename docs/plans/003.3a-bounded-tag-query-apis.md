## Goal

Add an end-to-end, read-only multi-tag content search: a typed bounded catalog API and the compatible `catalog tags find` CLI. Results group duplicate file instances by content identity and may show bounded current paths and all active tag names for each bounded content row.

## Matching semantics

- At least one requested tag is required. Validate every tag and deduplicate repeated names before querying.
- Matching defaults to `all`: every requested tag must have at least one active assertion on the content. `any` requires at least one requested tag to match.
- An optional `user|system` provenance filter applies independently to every requested tag. With `all`, every tag must have an active assertion of that kind.
- Multiple active provenance sources asserting the same requested tag do not multiply or otherwise strengthen a match.
- Retracted assertions never match.
- Content matching is catalog-wide, so tagged content remains discoverable after all paths disappear.
- Current-path counts and previews are scoped to the supplied `ROOT` and its latest successful scan. This keeps each relative path associated with one location. A matching content identity with no current path at that root remains visible with a path count of zero.
- Displayed tag names are all distinct active tags on the matched content, ordered alphabetically. They are not restricted to the requested tags or provenance filter.

## Public API

Add explicit immutable result types with the semantic equivalent of:

- A content search row containing content identity, size, complete current-path count at the requested root, bounded current POSIX paths, complete distinct active-tag count, and bounded alphabetical active-tag names.
- A search result containing bounded content rows, complete matching-content count, and the complete number of current paths at the requested root across all matching content.

Add a new `Catalog` query with the semantic equivalent of:

```python
search_content_by_tags(
    root,
    tags,
    *,
    match="all",
    provenance=None,
    limit=20,
    path_limit=20,
    tag_limit=3,
)
```

`limit`, `path_limit`, and an explicit numeric `tag_limit` must be positive. A distinct `None`/all-tags mode may request every distinct active tag only after content rows have been bounded. Results are ordered by full content algorithm and digest, not by shortened display values.

Preserve `Catalog.search_tagged_content()` and its `TaggedContentSearch` return type unchanged.

## Query shape and bounds

- Resolve matching content from active assertions with distinct requested tag names and explicit `all|any` grouping semantics.
- Compute complete matching-content and root-scoped current-path totals independently of the row limit.
- Apply the content limit before constructing content result objects.
- Fetch paths and tag previews only for the already bounded content IDs. Apply each path/tag preview limit in SQLite before those rows are materialized.
- A small sequence of focused SQL queries is preferred over one unbounded join. Do not introduce a general query-builder abstraction solely for this plan.
- Use the existing active-assertion indexes; do not change schema version 2.

## CLI

Extend the existing command compatibly:

```text
archiver catalog tags find ROOT TAG [TAG ...]
    [--match all|any]
    [--provenance user|system]
    [--limit N]
    [--details] [--path-limit N]
    [--display-tag-limit N | --all-tags]
```

- Existing one-tag invocations retain their syntax, default limit of 20, provenance filtering, and content-selection semantics. Their human-readable output intentionally changes to the new table.
- Render one row per content identity with `SHA-256`, `Size`, `Paths`, and `Tags` columns.
- `Paths` is the complete root-scoped current-path count, including paths omitted by row or preview limits.
- `Tags` shows alphabetical distinct active names. The default display limit is 3; overflow renders as `tag-a, tag-b, tag-c +N`.
- `--details` prints up to `--path-limit` current POSIX paths beneath each content row. `--path-limit` defaults to 20.
- `--all-tags` wraps tag continuation lines beneath the same bounded content row rather than widening the table without bound.
- Report complete matching-content and current-path totals and the effective `AND`/`OR` requested-tag expression.

## Implementation record

- Added public `TagMatchMode`, `ContentTagView`, and `MultiTagContentSearch` types and exported them from `archiver`.
- Added `Catalog.search_content_by_tags()` with active-assertion AND/OR matching, repeated-tag deduplication, optional provenance filtering, full-digest ordering, complete content/path totals, and bounded root-scoped path and alphabetical tag previews.
- Matching content remains catalog-wide while current-path counts and previews are restricted to the requested root's latest successful scan. Orphaned tagged content therefore remains discoverable with zero current paths.
- Parent content rows are limited before typed materialization. Window-ranked path and tag preview queries operate only on bounded content IDs; all-tags mode removes only the tag preview limit for those bounded rows.
- Extended `catalog tags find` with repeated positional tags, `--match`, `--details`, `--path-limit`, `--display-tag-limit`, and `--all-tags`. One-tag syntax and selection semantics remain compatible; human output now uses the planned width-aware table.
- Preserved `Catalog.search_tagged_content()` and `TaggedContentSearch` unchanged. Schema version remains 2 and no migration or persistent index change was introduced.
- Added `tests/integration/test_multi_tag_search.py` and `tests/integration/test_multi_tag_cli.py`, and updated the existing one-tag CLI expectation for the intentional table-format change.
- Validation: 106 tests passed and 3 skipped; Ruff lint and format checks, strict mypy, and `git diff --check` passed.
- No unresolved questions or deviations were identified. Plan 003.3b was not started.
