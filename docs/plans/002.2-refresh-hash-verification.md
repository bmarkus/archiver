## Goal and scope

Keep routine catalog refreshes fast through the existing metadata cache, and
offer explicit full SHA-256 verification when callers need fresh byte-based
observations. Record mandatory verification during future archive ingestion.
This is a new capability, not a correction to the documented cache behavior.

The original planning request did not activate implementation. The domain model and
invariants remain authoritative; earlier plans retain their historical outcomes.

## Existing behavior

`Catalog.reconcile_directory()` already reuses the previous successful scan's
content identity when relative path, size, and `mtime_ns` match. New paths and
metadata changes are hashed through `hash_file_stably()`. `scan_directory()`
reconciles and atomically applies the resulting change set. The CLI exposes
this workflow as `catalog refresh` and the compatible `catalog scan` alias.

Matching metadata is a cache heuristic. A same-size rewrite with restored mtime
can retain a stale cached identity until the file is actually hashed again.
Metadata never defines content identity.

## API contract

Extend the existing methods with a keyword-only option, preserving all current
parameters and return types:

```python
catalog.scan_directory(root)  # incremental refresh
catalog.scan_directory(root, verify_hashes=True)  # full verification

changes = catalog.reconcile_directory(root, verify_hashes=True)
catalog.apply_refresh(changes)
```

- Add `verify_hashes: bool = False` to both `scan_directory()` and
  `reconcile_directory()`. Forward the option through the convenience wrapper.
  Do not introduce a separate `refresh()` alias in this plan.
- Default/false preserves existing behavior: reuse an identity only for a
  matching path, size, and nanosecond mtime in the same location's latest
  successful scan. Hash new paths and metadata changes.
- True bypasses identity reuse and hashes every included regular file using
  the existing stable SHA-256 hashing boundary. Existing exclusions and
  symlink traversal rules still apply.
- Preserve the existing-path symlink/regular-file guard before choosing reuse
  or hashing. Bypass only the metadata-cache shortcut; do not weaken existing
  detectable file-type change checks or claim protection against all races.
- Compare freshly observed identities with the baseline to classify existing
  paths as `unchanged` or `modified`. A verification mismatch is an observed
  modification, not a reconciliation error. New and missing classification
  stays unchanged. Metadata-only changes with identical bytes are `unchanged`.
- `RefreshChange.hash_reused` is false for every fully verified observation,
  including unchanged content. Preserve existing summary and progress semantics.
  Progress reports one callback per completed included file and cumulative
  observed sizes, not bytes physically read or a new verification-byte counter.
  Missing paths produce no progress callback.
- `apply_refresh()` continues applying the captured observations atomically
  after its baseline check. It does not read or verify source files again.
- Full verification describes bytes read during reconciliation; it does not
  lock the filesystem or guarantee that files stay unchanged afterward.
- Read failures, detectable mutations during hashing, and callback failures
  preserve existing failure behavior and the most recent successful state.

## CLI contract

Add `--verify-hashes` to both `archiver catalog refresh ROOT` and
`archiver catalog scan ROOT`. Forward it to reconciliation, including with
`--dry-run`. Default behavior and existing output formats remain compatible.
Help text must distinguish metadata reuse from reading and hashing all files.
Existing `--details all` reporting must show hashes as rechecked during full
verification for unchanged paths, using the current `(hash rechecked)` suffix.
New, modified, and missing rows keep their existing formatting. A verified dry
run remains write-free; verification/read failures return nonzero and do not
print a successful completion or replace the current snapshot.

## Mandatory verification for future archive ingestion

An archive must verify the actual copied content with SHA-256 during every
ingestion, even when a source catalog already supplies an expected identity or
was recently fully verified. A cached source hash supplies the expected value;
it cannot substitute for reading and verifying the copied bytes.

Before accepting a managed copy as successfully ingested, the ingestion
operation must compare a freshly computed SHA-256 of the destination bytes
with the expected content identity. A mismatch, read/copy failure, or interruption
must not publish that copy as successfully ingested. There must be no option
to skip this verification based on matching size/mtime or cached hashes.
Verification of the source alone does not verify the resulting stored copy.

This is a requirement for a later ingestion plan, not authorization to implement
archive storage now. That plan must define staging/publication, cleanup and
recovery, concurrent mutation handling, and expected-identity selection when
the source catalog is stale. Its tests must include matching cached metadata
with changed source bytes and corruption of the copied destination.

## Design and invariants

- Keep the existing stable hashing interface and transactional application.
- Preserve byte-based identity and use metadata only to accelerate routine
  observations (invariants 1–6 and 22).
- Preserve successful-scan history, baseline checks, source read-only behavior,
  and failure atomicity (invariants 7–9, 19–20).
- No schema changes or migrations are required. Do not persist a verification
  timestamp or imply that old scan rows prove fresh verification.
- No new Archive class, ingestion operation, source mutation, merge policy,
  tag management, working-copy management, remote storage, watchers, GUI, or
  Rust implementation is included.

## Acceptance criteria and validation

- [x] Default and explicit false reuse hashes for matching metadata; count hash
  calls rather than relying on timing or performance assumptions.
- [x] True hashes every included regular file even with matching metadata,
  including nested paths, duplicate content, and empty files.
- [x] First scans hash all included files in either mode. An empty root can
  produce and apply an empty successful snapshot; removing all prior files
  reports them missing without invoking the hasher.
- [x] A same-size rewrite with deterministically restored `mtime_ns` remains
  cached during routine refresh and is detected as modified in verification.
- [x] Identical bytes remain unchanged after verification, with
  `hash_reused=False`; metadata-only changes retain the existing classification.
- [x] New, changed-metadata, missing, and renamed paths retain their existing
  semantics in both modes; exclusions and symlink rules remain enforced.
- [x] Reconciliation and CLI dry runs perform no database writes in either
  mode. Successful application persists verified observations across reopen.
- [x] Applying a verified change set records the captured observations even
  if source bytes change afterward; it does not rehash. A subsequent refresh
  uses its own selected mode. Historical observations and unrelated locations
  remain unchanged when a verified refresh publishes a new snapshot.
- [x] Hash/read failure, detectable concurrent mutation, callback interruption,
  stale baseline, and application failure preserve the previous successful
  snapshot. Source bytes, names, size, and mtime remain unchanged by scanning;
  tests must not require unchanged access times.

- [x] Progress counts and completed-file callbacks retain the existing meaning
