## Goal

Establish the smallest internal foundation for the query grammar by representing and executing one existing current-observation query through distinct description, compilation, and execution boundaries.

Route `Catalog.current_files(root)` through that path without changing its public contract. This proves the architectural boundary; it does not expose a fluent public query API or anticipate the complete grammar.

## Existing behavior to preserve

`Catalog.current_files(root) -> list[FileObservation]` remains unchanged:

- the root uses the existing catalog location rules;
- an unknown root or location without a current successful scan returns an empty list;
- rows represent only the location's latest successful scan;
- each row retains its location, relative POSIX path, full content identity, observed size, and observed mtime;
- rows are ordered by relative path;
- the catalog must remain open when the method executes;
- execution modifies neither source files, catalog data, nor schema state.

Existing callers, exports, pandas adapters, and CLI behavior remain compatible.

## Internal design

### Minimal query description

Introduce an immutable internal description sufficient to express exactly:

```text
current file observations for one resolved catalog location
ordered by relative path ascending
```

The description uses domain concepts. It must not contain SQL text, SQLite table or column names, a live cursor, or mutable parameter collections.

Do not add public filter expressions, generic projection, grouping, aggregation, tags, configurable sorting, or limiting in this subplan.

### Compilation boundary

Introduce a narrow SQLite-specific compiler or compilation function that accepts the internal description and produces an executable parameterized query representation.

SQL construction belongs behind this boundary. The design should allow later query nodes without moving SQL concerns into public query objects or `Catalog` methods.

Only the SQL shape required by `current_files()` belongs here. Do not build a general SQL framework, ORM, dialect abstraction, optimizer, or parser.

### Execution and materialization boundary

Introduce a narrow execution path that:

- executes the compiled query on the catalog's existing SQLite connection;
- materializes the existing `FileObservation` domain type;
- preserves deterministic relative-path ordering;
- does not commit, mutate persistent state, or access source files.

`Catalog.current_files()` resolves the location as today, creates the internal description, and delegates compilation and execution. It remains the only public entry point added to this path in 004.1.

## Validation

Add automated coverage demonstrating:

- equivalent `current_files()` results for normal and nested paths;
- deterministic relative POSIX path ordering independent of insertion or filesystem enumeration order;
- duplicate content at different paths remains distinct observations with the same content identity;
- empty files are preserved correctly;
- an unknown root and a known location without a successful current scan return an empty list;
- a later successful scan replaces current results while older observations remain historical;
- a failed or interrupted scan cannot replace the latest successful state;
- behavior persists across close and reopen;
- query success and failure leave source bytes and metadata, scan history, current-scan selection, and schema version unchanged;
- the internal description is immutable and contains no SQL-specific values.

Prefer extending focused integration tests where that remains clear. Add unit tests only when they directly establish the new internal boundary.

## Acceptance criteria

- `Catalog.current_files()` delegates through query-description, SQLite-compilation, and execution boundaries.
- Its public signature, return type, ordering, root behavior, and current-state semantics are unchanged.
- The internal description is immutable and contains semantics rather than SQL or SQLite identifiers.
- Compilation emits parameterized SQL and preserves current-location and latest-successful-scan constraints.
- Materialization produces `FileObservation` without catalog-wide history materialization.
- No public query grammar, new public export, persistent schema change, or source/catalog mutation is introduced.
- All required validation passes and the outcome is recorded here.

## Non-goals

Exclude:

- a public `catalog.current(...)` or other fluent query constructor;
- public predicate, sort, limit, projection, group, or aggregate operations;
- changes to `search_current_files()` or tag-aware searches;
- duplicate, tag, history, summary, pandas, or CLI migration;
- removal, deprecation, or renaming of an existing API;
- caching, prepared-statement management, snapshots, pagination, or asynchronous execution;
- persistent schema or index changes;
- source-file mutation, archive management, ingest, merge policy, working copies, remote storage, GUI behavior, background watchers, or Rust.

## Exit condition

After implementation and validation, record files changed, tests added, user-visible behavior, schema impact, architectural decisions, deviations, and command results. Mark only Plan 004.1 implemented and stop for review. Do not begin Plan 004.2 automatically.
