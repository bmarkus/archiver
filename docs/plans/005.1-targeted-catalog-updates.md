## Goal

Add a Catalog API that registers or replaces selected files and retires selected
paths without enumerating the entire directory. Initially persist a complete
successor snapshot by copying unaffected observations in SQLite. Introduce only
the boundaries needed to replace this with incremental database writes later.

This child performs no physical copying or deletion and implements no Archiver.
It is an independent prerequisite. Activated at the user's explicit request on 2026-11-12.

## Existing implementation and required semantic amendment

Schema version 2 uses `locations.current_scan_id` to select current observations
from `file_observations`. Each successful refresh stores a complete snapshot.
Current-file, duplicate, exact-path, summary, and reconciliation reads depend on
this representation. Duplicate handles pin scan IDs. `prune_history()` already
supports root-scoped transactional deletion of old observations and scan rows,
preserving content identities, tag history, running scans, and current state.

Before code changes, amend `docs/domain-model.md` and `docs/invariants.md` to
state explicitly:

- A completed inventory snapshot may originate from a full scan or from targeted
  observations/removals applied to an earlier committed inventory.
- Inherited records retain prior knowledge; targeted publication is not a claim
  that untouched paths were freshly observed or still physically exist.
- Failed publication cannot replace the committed inventory. Retained snapshots
  remain immutable; targeted updates create new snapshot identities.
- Explicitly selected publication retention may prune old snapshots atomically
  after successful replacement, preserving content and tag history.
- Inventories describe known file instances, not guaranteed directory coverage.
  Snapshot origin describes how a publication was produced, not completeness.
  Distinguish inherited snapshot membership from a fresh observation event in
  historical wording; do not imply inherited records were re-observed.

This is an explicit extension of scan-derived current state, not an in-place
mutation of historical evidence. Preserve historical plan outcomes and the
read-only meaning of scanning. If another authoritative conflict emerges, stop
design changes and report it before proceeding.

## Minimal boundaries

### Inventory revision and changes

Introduce immutable typed values for an inventory revision, a change set, and a
publication result. Exact exported names may follow existing conventions:

```python
changes = catalog.prepare_file_update(
    root,
    paths=[new_file, changed_file],
    remove_paths=[PurePosixPath("removed/file.txt")],
    verify_hashes=False,
)
result = catalog.apply_inventory_changes(changes, keep_last=2)
```

`paths` accepts a single Path or a collection of Paths; normalize a single value
explicitly. Paths are absolute or relative to the supplied root, never relative
to the process working directory. Removals use validated root-relative POSIX
paths. Empty collections are valid.

The change set includes catalog identity, location, an opaque baseline revision,
ordered upsert observations, and ordered removal paths. Internally the revision
may wrap the current scan ID; Archiver must not interpret it or access tables.
Scope revisions to their catalog and location, not just a raw integer.

The result reports the new/current revision, snapshot origin, inserted/replaced/
removed counts, and retention outcome. Distinguish changed-path counts from
complete inventory totals. An empty input is a no-op: no snapshot and no pruning.
Every nonempty valid request publishes a successor, even when all supplied files
match cached content and metadata. Such upserts count as replacements of existing
path records, not necessarily content modifications. Publication advances the
revision and applies retention. Empty requests do neither; applying an empty
change set still checks its catalog/location scope and baseline for staleness.

### Observation boundary

Preparation reads only supplied files and writes no database records. Reuse
existing stable hashing, path validation, exclusions, and unchanged-metadata
cache rules; `verify_hashes=True` forces fresh hashing. New files always hash.
No recursive enumeration or directory creation occurs. Any observation failure
fails preparation without publishing a partial change set.

Capture the baseline once and pin all cached-observation reads and removal
validation to that exact snapshot, never to a repeatedly resolved current pointer.
Use a consistent database read scope for baseline-dependent reads; any cached
records retained outside it must remain tied to the captured revision. Do not
hold a write transaction while hashing. A concurrent publication may make the
prepared change set stale, but must never cause preparation to mix snapshots.
If pruning makes required baseline records unavailable, fail preparation clearly
rather than treating them as absent/new. Test publication and pruning during
preparation as well as between preparation and application.

Reject nonregular files, symlinks and paths traversing symlink ancestors,
out-of-root paths, catalog database artifacts, duplicate normalized paths, and
paths present in both upserts and removals. Do not silently deduplicate ambiguous
input. Preserve root/path scope and deterministic POSIX component ordering.

Validate the original supplied path and its symlink ancestors before canonical
resolution can hide a link. Reject aliases of the same destination path within
the request, including case aliases on case-insensitive filesystems and aliases
between upserts and removals. Match an existing baseline destination consistently
so an alternate spelling cannot create a second inventory entry for the same
path. Preserve distinct hard-linked pathnames as distinct file instances; shared
content or inode alone is not a duplicate-path error. The existing hashing
function checks regular-file stability, not ancestor safety or path aliases;
add the narrow path guard required here. State the limits of ordinary path checks
under external filesystem races rather than promising filesystem locking.

Removals retire inventory records only; they do not assert or perform a physical
deletion. Require each removal to identify an existing baseline instance and
reject unknown removals. This supports future Archiver registration of successful
deletions without re-reading already deleted files.

An initially unscanned root may receive additions, producing a targeted inventory
containing only registered files. It must not claim a complete directory scan.
Unknown-root removals fail. Full refresh can subsequently observe the entire root.
No coverage field is added: both partial and inherited inventories represent
known instances. Public summaries and examples must not infer complete directory
coverage from origin, snapshot success, or the presence of a prior full scan.

Future Archiver code may use a narrow internal constructor for observations
produced by its verified destination-copy workflow. Do not introduce a public
shortcut accepting arbitrary caller-asserted hashes or mutable SQL access.
Catalog validates constructed changes; filesystem verification remains the
responsibility of the trusted observation boundary.

### Publication boundary

Use one internal transactional publication boundary shared by full refresh and
targeted updates, while allowing their observation/preparation paths to differ.
Keep it a concrete private function or small class, not a backend framework.

Archiver supplies changes and a retention policy; it does not copy database rows,
interpret scan IDs, or invoke pruning SQL. Query internals may remain snapshot-
based. Future incremental writes will still require query and pinned-reader
design work; this plan does not promise a cost-free backend replacement.

## Snapshot publication algorithm

1. Validate types and change-set structure before writes. Reject an already-open
   transaction without committing or rolling back the caller's existing work.
2. Use `BEGIN IMMEDIATE` to acquire the SQLite write lock before baseline reads,
   with foreign-key enforcement enabled. Apply this ordering to the shared
   full-refresh publication path as well.
3. Resolve the location and compare the current revision to the captured baseline.
   A competing full refresh or targeted update makes the change set stale.
4. Insert a new snapshot row with origin `targeted_update`.
5. Stage affected paths in transaction-local SQL storage, or use an equivalently
   bounded SQL method that avoids SQLite parameter-count limits.
6. Copy baseline observations except affected paths with `INSERT ... SELECT`.
   Do not build a Python map/list of the entire baseline.
7. Resolve/insert content identities and insert upsert observations. Removals
   contribute no observation to the successor. Untouched records retain their
   metadata; no file access is needed during database publication.
8. Mark the snapshot completed and advance the current pointer.
9. Apply retention in the same transaction, then commit. Clear staging resources
   on success and failure so later operations cannot see stale staged paths.

Any failure, including retention failure, rolls back the entire publication and
preserves the prior current pointer and retained history. A failed preparation
or publication creates no successful snapshot. Do not hold a write transaction
while hashing files. The baseline check protects catalog consistency, not the
filesystem against changes after observation.

Snapshot copying is O(total baseline paths) database work per batch, with temporary
space for old and new snapshots. This is accepted initially. Do not publish one
snapshot per copied file by default in future Archiver code; use batches.

## Retention contract

- Targeted publication defaults to `keep_last=2`. Positive integers retain that
  many newest successful snapshots for the location; `None` retains all.
  Reject booleans, zero, negative, and out-of-range counts eagerly.
- Full and targeted snapshots share the same retention sequence. With fewer than
  two successes, retain all available successes. Never prune another location.
- Add an optional publication-retention keyword to existing full-refresh/apply
  and scan convenience APIs, defaulting to keep-all for compatibility. Future
  Archiver passes its default of two explicitly, including requested full scans.
- Policy is supplied per operation initially; no persisted settings table is
  required. Standalone explicit `prune_history()` keeps its existing signature
  and defaults. Refactor its transactional deletion internals for safe reuse;
  do not call its public transaction-owning method from inside publication.
- Automatic publication retention does not delete failed or running snapshots.
  Existing opt-in failed-history cleanup remains explicit.
- Content identities and all tags/assertion/retraction/provenance records remain.
  No automatic VACUUM or content garbage collection occurs. Deleted pages are
  reusable; immediate reduction of database file size is not promised.
- Close active query/history streams before publication with pruning. Retained
  pinned duplicate handles continue working; pruned handles fail clearly rather
  than reading members from a different snapshot. Keep-all permits existing
  pinned-snapshot behavior. Document this lifecycle boundary prominently.

## Schema and compatibility

Create schema version 3 with one required persistent addition:

```sql
scan_runs.origin TEXT NOT NULL
    CHECK (origin IN ('full_scan', 'targeted_update'))
```

Full refresh inserts `full_scan`; targeted publication inserts `targeted_update`.
Keep existing snapshot tables, indexes, current pointer, and foreign keys.
Do not add permanent parent-snapshot references, operation journals, a current-
inventory table, per-file provenance, or a second backend in this child.

Expose origin in snapshot/history summaries and update API documentation so a
targeted update's timestamps/totals are not described as a fresh full-directory
scan. Preserve existing public method names and query result semantics; extend
public model fields compatibly where practical and test the API contract.

No version-1 or version-2 migration is implemented. Both `Catalog.open()` and
`Catalog.migrate()` must reject those versions without writes and explain that
an explicit rebuild is required. Keep the migration API/CLI entry points;
`migrate()` on a valid version-3 database returns False (already current).
Other unsupported versions continue to fail clearly without writes.

The existing migration implementation adds tag tables and then assigns
`SCHEMA_VERSION`. Merely bumping that constant would incorrectly label an old
database version 3 without adding `origin`; replace that legacy migration branch
with the explicit rejection above. Update the version-1 open error, CLI guidance,
and legacy migration tests to match this intentional compatibility change.

Do not reinterpret old schemas or recreate databases implicitly. Rebuilding means
creating a separate new Catalog and explicitly scanning; it reconstructs file
inventory but not user tags/provenance. Never silently delete the old database.

## Concrete use cases

### Target additions during sync (later child)

After successful copy, destination verification, and no-overwrite publication,
Archiver supplies fresh destination observations in a batch. Catalog creates a
successor containing the old inventory plus those additions/replacements. The
source inventory is unchanged. A later full refresh reconciles normally.

### Local dedup removals (later child)

For two paths with content H, Archiver verifies a survivor and deletes only an
authorized redundant instance. Catalog removes that instance from the successor
inventory; H and its tags survive. Failed physical deletions are not registered
as successful removals. No per-content existence tag is introduced.

Filesystem changes cannot participate in SQLite rollback. A later Archiver child
must report copy/delete success followed by publication failure as requiring
reconciliation. This child tests database failure semantics without implementing
filesystem mutation or recovery orchestration.

## Non-goals

No Archiver class, actual sync/dedup, physical deletion/copy, cross-catalog
comparison, operation-summary schema, CLI workflow expansion, automatic watchers,
database migration project, delta chains, mutable historical snapshots, or truly
incremental database writes. No optimization beyond keeping baseline row copying
inside SQLite. No change to content identity or tag semantics.

## Acceptance tests

1. Single and multiple new files, nested paths, empty files, and duplicate content
   register correctly; unchanged matching metadata reuses hashes and forced
   verification hashes again. No unrelated directory traversal/hashing occurs.
2. Replacing a path updates its current identity/metadata; removing a path retires
   only that instance. Shared identities/tags remain, including after removing
   their last current instance. Unknown removals and conflicting inputs fail.
3. Unaffected paths survive successor publication unchanged. Initial targeted
   registration works without claiming full-directory coverage; empty input is
   a write-free no-op that still rejects stale/foreign change sets. Nonempty
   unchanged updates publish, advance revision, and apply retention with accurate
   replacement counts. Large batches exceed ordinary SQL placeholder limits safely.
4. Retained historical snapshots remain immutable, with distinguishable origins.
   Current files, duplicates, content path views, tags, summaries, and exact-path
   resolution all reflect the published inventory; reopen preserves results.
5. A full refresh after mixed additions/replacements/removals sees the actual
   filesystem correctly, including paths intentionally retired while physically
   present. Both refresh and targeted publication invalidate older baselines.
6. Injected observation, SQL-copy/insert, current-pointer, and retention failures
   preserve the prior committed inventory/history with no leaked staging state.
   Subsequent publication still works. Test competing connections deterministically.
   Preparation reads one baseline during concurrent publication/pruning and fails
   clearly if required history becomes unavailable. Publication takes its write
   lock before validating the baseline. An existing transaction is rejected with
   its pending work untouched, for both full and targeted publication.
7. Default targeted retention keeps the latest two successful snapshots; explicit
   counts and keep-all work. Full-scan and targeted origins count together. Other
   locations, current/running/failed rows, content, and tag history remain safe.
8. Existing full-scan defaults preserve history; explicit keep-two full publication
   prunes atomically. Standalone pruning preview/application behavior is preserved.
9. Retained pinned duplicate reads work; pruned handles fail clearly. Cover the
   documented reader-close boundary and reopen persistence after retention.
10. Invalid types, out-of-root paths, symlinks/ancestor symlinks, nonregular files,
    database artifacts, foreign-catalog change sets, and foreign-location revisions
    fail safely. Every Catalog operation leaves physical source files unchanged.
    Cover case aliases on case-insensitive filesystems, aliases of baseline paths,
    mixed upsert/removal aliases, ancestor checks before resolution, and distinct
    hard-linked paths. Use capability-based skips where filesystem support differs.
11. New databases have explicit version/origin constraints and enforced foreign
    keys; unsupported versions fail without writes. Documentation accurately
    explains rebuild/tag limitations and accepted O(N) database publication cost.
    Open and migration attempts on versions 1 and 2 leave their databases unchanged
    and give rebuild guidance; migration of valid version 3 is a no-op. Origin and
    successful publication never imply directory-completeness guarantees.

Use temporary directories, fixed metadata where needed, deterministic failure
injection, and no network/user-archive dependencies. Check filesystem bytes and
relevant metadata before/after read-only operations. Do not use wall-clock races.

## Implementation outcome — 2026-11-12

The user explicitly activated this child after the draft review. This outcome
supersedes the earlier draft-only planning notes. Plan 005.2 is not activated.

Implemented `prepare_file_update()` and `apply_inventory_changes()` with typed
`InventoryChanges`, opaque `InventoryRevision`, and `InventoryUpdateResult`.
Full and targeted publication share `_publish_inventory()`. Selected baseline
records are read in one read transaction, cached only for the requested batch,
and hashed after that transaction ends. Publication uses `BEGIN IMMEDIATE`, SQL
successor copying, and atomic retention. Nonempty unchanged requests publish;
empty requests validate scope/baseline without snapshot creation or pruning.

New catalogs use schema 3 with `scan_runs.origin`; full-scan is its default for
existing explicit inserts within the new schema. There is no implicit legacy
upgrade: versions 1 and 2 are rejected without writes by open/migrate, with rebuild
guidance. Domain/invariant amendments are implemented. Origins are exposed in
scan/history records and CLI info/history. Current query behavior and the
standalone pruning API/defaults are preserved.
