## Relationship to Plan 001

Plan 001 established persisted locations, scan runs, content identities, and file observations. This subplan exposes those existing historical records through typed, streaming inspection APIs.

It does not change the SQLite schema, scanning transactions, current-state promotion, or content-identity semantics established by Plan 001.

## Goal

Make catalog history available for debugging and exploration without requiring callers to write raw joins over the SQLite schema.

## Public API

- `ScanRun` represents one catalog-local scan event, including its location, status, and timestamps.
- `HistoricalObservation` represents a persisted file observation with its associated `ScanRun`.
- `Catalog.scan_history()` lazily yields all scan runs, including empty and failed scans.
- `Catalog.observation_history()` lazily yields all persisted observations across locations and scans.

Both APIs use deterministic ordering. Observation history is ordered by location root, scan ID, then relative path; scan history is ordered by location root and scan ID.

## Design decisions

- History rows are typed domain objects, not raw `sqlite3.Row` values or pandas DataFrames.
- `FileObservation` remains the compact projection used by current-state APIs.
- The shared internal observation join now produces `HistoricalObservation` values. Current-file, content-lookup, and duplicate-group queries retain SQL-side filtering, so they do not load catalog-wide history into memory.
- History APIs stream from SQLite cursors. A caller may explicitly materialize a list or DataFrame when needed for exploration.
- Persisted observations from failed or running scans are included if a later implementation retains them; their scan status remains visible. The present transaction behavior rolls back failed-scan observations.
