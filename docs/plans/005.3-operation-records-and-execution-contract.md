## Goal and scope

Define and implement the operation model that later sync and local deduplication
executors must obey. Synchronization uses the agreed **temporary, operation-scoped
SQLite database** for its manifest and progress. The target Catalog remains the
permanent inventory; the workspace is neither a merged Catalog nor another archive.

This child owns workspace records, bounded storage/read APIs, explicit managed-root
authority, operation summaries, publication receipts, and interruption/recovery
contracts. It does not copy or delete content files and does not expose a working
`execute()` method. Public examples must not imply that execution exists yet.

The sync model here is a model of proposed actions and their outcomes, not a new
content identity model. Reuse `ContentId`, catalog UUIDs, `Location`, and opaque
`InventoryRevision` semantics. A manifest entry is proposed work, never evidence
that its destination exists. Tags remain content metadata, not progress flags.

Writing this plan does not activate this child or authorize filesystem execution.

## Authority and scope

- Sync identifies source and target Catalog handles, UUIDs, canonical roots, and
  captured revisions. The source is read-only. Execution authority, supplied
  explicitly by the caller in 005.4, permits creating new files below the target
  root; it never permits overwriting existing files or deleting source files.
- Dedup identifies one Catalog/root and an explicit deletion authority supplied
  in 005.5. No destination is required. Planning grants no deletion authority.
- Persist the operation kind and scope for inspection, but do not persist a
  reusable permission token. Reopening a workspace requires fresh caller authority
  matching its recorded scope before any physical execution.
- Reject symlink roots/ancestors, escaping or absolute manifest paths, and path
  aliases using the existing filesystem safety rules. Retain POSIX relative path
  representation inside the workspace; native paths are derived at the boundary.
- Sync source and target roots must be physically disjoint: reject identical or
  nested roots, including detected aliases. Distinct roots in the same Catalog
  remain supported. Copied databases sharing a UUID are not the same endpoint;
  verify the supplied database files and roots as well as UUIDs when reopening.
- Catalog, workspace, SQLite sidecars, and future in-flight copy artifacts are
  control artifacts, never manifest content. Prefer a workspace outside both
  content roots, and require that placement in this child.

Invariants 1–4, 7–11, and 15–22 apply. No domain/invariant amendment is expected:
explicit operations may have authority, while planning remains observational.
Report a conflict before implementation rather than weakening those rules.

## Temporary SQLite workspace

### Placement, ownership, and compatibility

Require an explicit workspace parent directory outside both roots. Create a new
operation-owned directory exclusively, containing `workspace.sqlite3`; return its
absolute path and operation UUID to the caller immediately. Never reuse an existing
directory or overwrite an existing database. There is no prescribed archive layout.

Use `sqlite3`, foreign-key enforcement, explicit transactions, and durable commits
with `synchronous=FULL`; initially use rollback journaling to simplify ownership
and disposal. No database write transaction spans file copying or hashing.
SQLite durability still depends on the filesystem and storage device.

The workspace has its own format version, initially 1, independent of the Catalog
schema version. Validate required tables, constraints, scope and format on reopen.
Reject unknown/malformed formats without writes or automatic rebuilding. A closed
handle releases connections; it does not delete the directory. Do not use an
unconditionally cleaned-up temporary-directory context for recovery evidence.

Allow one active controller per workspace using an explicit exclusive lease
artifact created without replacement. An unclean exit may leave it behind.
Recovery requires explicit takeover after the caller ensures the old controller
has stopped; never infer exclusive ownership from a PID or timeout alone.

### Records

Use typed immutable public records with internal SQLite tables along these lines:

| Record | Required data |
| --- | --- |
| Workspace header | Format version, operation UUID/kind, optional predecessor UUID, creation time, lifecycle state/interrupted phase, source/target UUIDs and roots, database paths for reopening, captured revisions, retention policy, comparison totals. |
| Manifest entry | Stable entry ID, full expected content identity and size, selected source-relative path and cached metadata, nullable proposed target-relative path, classification, action (`copy`, `skip_present`, or recovery-only `register_existing_verified`), execution state, optional predecessor entry reference, error code/detail. |
| Verification/progress evidence | Entry ID, placement protocol version, owned staging directory and witness-relative path, witness filesystem/file identifier, committed placement intent and proposed destination, verification algorithm/digest/size and destination metadata, placement outcome. |
| Finalization evidence | Operation UUID, expected target revision, frozen request version/digest and immutable entry selection/counts, finalization state, returned committed revision and summary/receipt when acknowledged. |

Encode revisions using a versioned internal representation with strict decoding;
do not make their private fields a new public API. Persisting a revision does not
make it valid against another Catalog or later inventory.

One manifest row represents one distinct source identity. Enforce unique full
identity and deterministic entry traversal by `(algorithm, digest)`. Already-present
content is classified separately and has no copy destination. Missing content may
have an unresolved destination during building; readiness requires every copy
candidate to have a valid destination and unique destination reservation. 005.4
defines collision naming and filesystem-specific alias reservation, including
file-versus-directory conflicts. Do not treat a SQL text uniqueness constraint as
sufficient native-path validation.

Expose bounded insertion, ordered batch iteration, entry outcome updates, and
complete SQL summary reductions. Default storage/read batch maximum is 1,000
records; callers may choose a positive integer maximum. Reject booleans and
invalid bounds eagerly. Never load the complete manifest or destination set in
Python. SQL storage/sorting may grow with the operation; bounded Python memory
does not imply constant disk space or constant startup time.

### Placement evidence contract

Workspace format 1 includes placement protocol `retained_link_v1`. 005.3 owns
its record validation and recovery decisions; 005.4 implements and capability-tests
the filesystem steps. Do not postpone the required evidence fields to 005.4.

1. Before creating artifacts, commit the entry's exclusive operation-owned staging
   directory/name and intended destination. The staging directory is on the target
   filesystem and excluded from catalog inputs, as are its contents.
2. Copy into a new regular staging file, freshly SHA-256 verify it, and commit its
   filesystem/file identifier plus expected identity, size and placement intent.
   Keep this staging file as a witness until finalization is acknowledged.
3. Place the destination by creating a hard link to the verified staging file with
   no replacement. This is a placement primitive, not duplicate-resolution policy;
   after witness cleanup the destination is the remaining link to the new copy.
   The witness is not an archive copy or a working-copy management feature.
4. If placement acknowledgement is lost, require the owned witness to remain a
   regular file with its recorded identifier, and the destination to refer to that
   same physical file. Freshly hash the destination and compare expected identity
   and size before recovering `placed`. Matching hashes or inode numbers without
   the retained witness and committed intent are insufficient. File identifiers
   are ownership evidence here, never content identity.
5. A missing destination can return to `pending` only before request freeze and
   after verifying that no uncertain placement remains. A different destination
   is an explicit conflict; a missing/replaced witness or contradictory evidence
   requires reconciliation, never inferred ownership or replacement.

005.4 must reject execution on filesystems lacking reliable same-file identifiers
or no-replace hard-link creation before any content copies. It must test these
capabilities and the durability ordering for supported local filesystems. No
rename-only fallback is implied. Another placement protocol requires an explicit
plan/format compatibility amendment before use. Quiescent-root and external-writer
limitations still apply; this protocol does not claim power-loss-proof behavior
on every filesystem. Lost durable evidence produces recovery guidance, not a guess.

### States and accounting

Workspace lifecycle:

| From | Permitted next state and condition |
| --- | --- |
| `building` | `ready` after exhausted comparison, matching counts and structural checks; `failed` on a known planning failure; `discarded` explicitly. An interrupted build is inspection/discard only, never resumed into readiness. |
| `ready` | `executing` after authority, ownership and revision checks; `failed` on pre-execution rejection; `discarded` explicitly. |
| `executing` | `finalizing` after all outcomes are known and the request is frozen; `recovery_required` on interruption, stale revisions or uncertain outcomes. |
| `finalizing` | `completed`, `partial` or `failed` only after a matching terminal receipt; otherwise `recovery_required` on interruption or publication failure. |
| `recovery_required` | `executing` only with no frozen request, unchanged baselines, fresh authority and resolved physical outcomes; `finalizing` only for an unchanged frozen request revalidated for retry; a terminal receipt's status after acknowledgement; `discarded` explicitly after receipt resolution. |
| `completed`, `partial`, `failed` | No execution/republication; acknowledge/clean up, or explicitly discard a retained pre-execution failure. |
| `discarded` | No further work; keep a minimal discarded/superseded summary in the Catalog if execution had started. |

On exclusive takeover, a saved `executing` or `finalizing` state is treated as
`recovery_required` before work resumes. Record the interrupted phase and whether
a frozen request exists. Receipt lookup comes first, even for a terminal-looking
workspace; a matching receipt determines the original committed outcome. Missing
or unreadable receipt information is not proof of noncommit. Inspection-only
reopening performs no transitions, cleanup, or execution. Illegal transitions fail
without writes; recovery never silently changes captured baselines.

Entry execution states are `pending`, `copying`, `verified`, `placed`, `skipped`,
`conflict`, and `failed`. Already-present rows are terminal catalog-based skips;
their presence is not physically verified. `placed` means verified bytes were
successfully placed, not registered in the Catalog. Inventory registration is
established by the operation receipt. Persist transitions transactionally and
reject illegal transitions; recovery can demote uncertain outcomes after checking
the filesystem. A saved verification flag alone never permits registration.

Complete summaries use SQL, independent of page limits. Distinguish planned
identities/bytes, catalog-based skips, placed files/bytes, conflicts, failed files,
unattempted entries, and registered files/bytes. Empty files count as files with
zero bytes; duplicate source paths do not inflate content counts. Operation status
and counters must not imply a full-directory completeness check.

`completed` means all intended entries were resolved successfully, including
catalog-based skips. `partial` means a finished attempt had failed/conflicting or
unattempted entries but any eligible successes were finalized. Neither status
permits unresolved physical outcomes or uncertain inventory commit status;
those require recovery. A finalized attempt with no registered successes and only
unsuccessful copy outcomes is `failed`, with a terminal zero-registration receipt.
Mixed successful skips and unsuccessful outcomes are `partial`; an empty/all-skip
successful attempt is `completed`. A pre-execution `failed` plan has no execution
receipt and is distinguishable by its phase and absence of a Catalog start record.

## Permanent operation summary and receipt

Persist minimal operation records in the target Catalog for sync, and in the local
Catalog for dedup. Do not write any operation rows to a distinct source Catalog.
Planning writes only the workspace; create a Catalog operation row when execution
actually starts. With one Catalog and disjoint roots, operation bookkeeping shares
that database but source inventory, content metadata, and tags remain unchanged.

Records contain operation UUID, kind, explicit scopes and source identity where
applicable, start/end times, status, aggregate outcome counters, and optional
committed inventory revision. Store no permanent per-file manifest or tag copies.
Expose exact-ID reads and bounded ordered operation-summary reads; timestamps
describe events, not identity or ordering tie-breakers without the operation UUID.

Use schema 4 for these tables/constraints. Opening schema 3 must fail without
writes and point to explicit migration. Provide a narrowly additive, transactional
`Catalog.migrate()` upgrade from validated schema 3 to 4, preserving UUIDs,
inventories, revisions, history, tags, retractions, and provenance. Validate before
changing anything; injected failure must roll back additions and the version.
Versions 1 and 2 retain their existing no-write rebuild guidance; unknown versions
fail clearly. Migration on valid schema 4 is a no-op. This limited upgrade avoids
requiring a rescan that would lose existing user metadata; it is not a general
legacy-migration project. No schema changes occur while writing this draft.

Define an internal Catalog operation-finalization hook at the existing publication
boundary. Within one Catalog transaction, it checks the baseline under the write
lock, publishes inventory changes if nonempty, applies retention, and writes the
terminal summary plus unique operation-ID receipt. The receipt stores original
committed revision and registration counts independently of retained scan rows,
so pruning cannot erase the evidence or cascade-delete the receipt.

Test this hook using small database-only change sets in 005.3. 005.4 adds bounded
manifest ingestion through this boundary; Archiver never writes inventory tables
directly. Zero-success finalization records a terminal summary/receipt without
creating a snapshot or pruning history.

On retry, check the receipt before checking an old baseline. An existing matching
receipt returns the original result without publication or counter increments;
reject mismatched kind/scope/request identity. Freeze the finalization request
before submission and persist a digest over its deterministically ordered entries,
scope, baseline, retention and outcome counts. Validate that digest on retry;
compute it incrementally. This is an integrity/idempotency key, not file identity.
An old receipt remains valid even if later operations have advanced current state.

Freeze is a workspace transaction that persists the exact selected entry records,
observation metadata, counts, scope, baseline, retention and canonical encoding
version together with their digest. The Catalog receipt check is repeated inside
the finalization write transaction before baseline validation. A frozen request is
immutable: retry never recomputes its digest from changed manifest outcomes.
Fresh verification results are separate recovery evidence, not edits to its
recorded observation metadata.

With no receipt and unchanged baselines, retry the same request only if every
selected destination still satisfies its recorded observation and placement
evidence. If an entry is missing, modified, replaced, ambiguous, or no longer
eligible, do not shrink the set or change counts under the same operation UUID.
Keep `recovery_required` and require explicit replacement planning. A baseline
change follows this same replacement rule. Before abandoning an old request,
establish absence of its receipt under the Catalog write lock and mark its started
operation `superseded`; finalization must reject superseded/discarded operation IDs.
If a receipt exists instead, acknowledge it and do not replace its committed work.

Explicit replacement planning creates a new workspace and operation UUID, records
the predecessor UUID, and captures fresh revisions. Consume old placement evidence
in bounded batches: for identities still requested by the new source inventory,
freshly verify matching owned destinations and plan `register_existing_verified`
at their existing paths instead of copying or renaming them again. Do not infer
this action from bytes alone or adopt conflicting/ambiguous destinations. The new
attempt publishes these observations and any new verified copies once through the
same Catalog boundary. Files no longer requested, or lacking adequate ownership
evidence, stay untouched and require explicit targeted Catalog reconciliation;
never silently omit them from the recovery report. This is explicit recovery,
not ordinary collision handling or automatic adoption of arbitrary existing files.
005.4 implements this construction using 005.3's evidence/request records. Preserve
the predecessor workspace until handoff evidence is durably recorded and its
artifacts have been resolved; superseding it alone is not permission to clean it.
An evidence handoff includes the witness identifiers, exact paths and ownership
references needed for the successor to validate and eventually clean each artifact.
The predecessor cannot clean a transferred witness before the successor resolves
it; persist acknowledgement in both workspaces, retaining both if acknowledgement
is interrupted. No handoff requires loading the whole manifest into Python.

## Execution and recovery contract for later children

1. Before execution, validate explicit authority, workspace ownership, and both
   captured inventory revisions. A stale plan causes no physical work. Close
   comparison readers before execution/finalization and retention.
2. 005.4 copies in bounded batches with per-entry progress commits. Record intent
   and an operation-owned temporary name before creating a copy artifact. Verify
   the actual destination-filesystem temporary bytes with fresh SHA-256 before
   no-overwrite placement. Never hold a Catalog write transaction while copying.
3. Check revisions at batch boundaries. If the source revision changes, stop
   further work and retain recovery evidence; do not silently select a new source
   inventory. Already placed copies stay in place. Revalidate source and target
   revisions before finalization; mismatch requires explicit replanning, not an
   automatic rebase. A new plan uses a new operation UUID.
4. Before finalization, revalidate placed destinations against expected identity,
   including fresh hashing on recovery and whenever saved evidence is uncertain.
   005.4 must specify the verification-to-publication sequence and detect observable
   replacement/modification. No claim of atomicity against arbitrary external
   filesystem writers is possible; require quiescent managed roots for reliable
   execution and document residual races. Source revision changes are not a
   substitute for checking source bytes during copying.
5. Normal partial copy failure may finalize verified successes once. A failed
   finalization rolls back inventory, pruning, summary and receipt together;
   physical files remain and the workspace becomes `recovery_required`.
6. Recovery first checks the Catalog receipt. If committed, report its original
   result and finish workspace acknowledgement/cleanup without publishing again.
   Do not reinterpret later destination changes as failure of the original commit.
7. Without a receipt, validate revisions and inspect uncertain entries. A crash
   may occur after placement but before its progress commit: inspect the proposed
   destination, never copy over it. Matching bytes alone do not prove this attempt
   placed them. Recover placement only with sufficient operation-owned evidence;
   otherwise report ambiguity and require explicit reconciliation/replanning.
   Use the `retained_link_v1` evidence contract above; 005.4 implements its filesystem
   capability checks and crash-point tests. Never infer ownership from matching
   content alone. A frozen selection may only be retried unchanged or superseded
   through explicit replacement planning as specified above.
8. Recovery does not automatically scan roots, delete placed files, or overwrite
   conflicts. Stale baselines or ambiguous physical outcomes retain the workspace
   and report its path. Explicit discard removes recovery evidence, not data files,
   and warns that physical changes may still need reconciliation.

The local dedup child reuses scope, summary, and receipt semantics. Its deletion
evidence, survivor checks and non-atomic deletion/publication recovery must be
specified in 005.5 before deletion exists. This child does not require a persistent
per-file dedup manifest or introduce a second inventory for local deduplication.

## Disposal

Disposal depends on receipt certainty and resolved physical outcomes, not whether
the result word is `failed`:

| Situation | Disposal rule |
| --- | --- |
| Matching terminal receipt, all physical outcomes known, all owned in-root artifacts resolved | Automatically close and remove owned workspace artifacts/directory, including for a finalized all-failed attempt. |
| Failed/interrupted finalization, no confirmed receipt, stale baseline, unreadable Catalog or ambiguous physical outcome | Retain workspace and placement witnesses; no automatic cleanup. Explicit recovery or discard is required. |
| Confirmed receipt but unresolved artifact cleanup | Preserve the committed result, retain workspace/path and report cleanup pending; retry cleanup only. |
| Planning/pre-execution failure or interrupted build | Retain for inspection; explicit discard may remove its owned workspace because no physical execution occurred. |
| Superseded attempt | Retain until durable evidence handoff and artifact resolution, then allow explicit disposal. |

The executor first resolves owned staging artifacts under its evidence checks;
generic workspace disposal never removes them. Cleanup failure never changes a
receipt or republishes inventory. Explicit discard of a started attempt must first
resolve receipt lookup under the Catalog write lock: acknowledge an existing
receipt or mark the uncommitted operation discarded, preventing future submission.
If the Catalog cannot be checked, retain the workspace. Discard reports every
unresolved physical effect and does not remove destination files. Minimal Catalog
discard/supersession summaries preserve the fact that registration did not commit;
they are not success receipts. A physical deletion is never rolled back by discard.

Validate the workspace marker, operation UUID, exact parent and owned names before
removal. Never recursively delete caller-provided directories or unknown files;
unexpected contents block automatic cleanup. Do not delete destination content
or in-root copy artifacts through generic workspace disposal. Artifact handling
belongs to the executor's verified ownership checks. No automatic expiry,
background recovery, or operation-history pruning is introduced.

## Acceptance tests

1. Create/close/reopen workspaces; preserve UUID, version, revisions, scopes and
   records. Existing paths, wrong scopes, corrupt data, unknown formats, and
   overlapping/symlink/escaping roots fail without changing content or inventories.
2. Large synthetic manifests, duplicate/empty content and nested paths support
   bounded insert/read/update batches, deterministic traversal and complete SQL
   counts. No whole-manifest Python materialization or per-entry Catalog lookup.
3. Interrupted builds remain unready; ready validation rejects duplicate identities,
   unresolved/aliased destinations and invalid counts. Injected transaction failure
   leaves the last committed workspace state intact and later writes usable.
4. Exercise legal and illegal state transitions, competing controllers, retained
   leases, explicit takeover, partial/all-failed/empty attempts and truthful counters.
   Cover every transition-table row, interrupted phase and read-only inspection;
   reopening never silently resumes physical execution or grants authority.
5. Planning success/failure leaves both Catalogs and content files unchanged.
   Simulated execution records only target/local summaries; source inventory and
   tags remain unchanged, including shared-Catalog roots. Reopen preserves records.
6. Schema-3 migration preserves all data and identity/revision semantics; rollback
   injection leaves the old schema intact. Legacy/unknown opens and migrations
   fail without writes as specified; foreign keys and required constraints hold.
7. Database-only finalization atomically commits a small change set, retention,
   summary and receipt. Failures at insertion, pointer update, pruning, summary
   and receipt roll back all of them. Existing caller transactions are rejected
   without changing caller work; stale revisions publish nothing.
8. Zero-success finalization makes no snapshot and prunes nothing. Matching retries
   return the original receipt; altered requests fail. A lost acknowledgement,
   later publication and pruning of the original snapshot never cause republishing.
9. Recovery decision tests inject interruption at progress commit, finalization,
   receipt acknowledgement and cleanup. Use fake filesystem/verification boundaries;
   prove saved success flags or matching bytes alone cannot authorize registration.
   Validate all `retained_link_v1` fields and decisions: retained same-file witness,
   missing/replaced witness, different/missing destination and unsupported protocol.
   Real hard-link capability/crash tests belong to 005.4. Test frozen-request retry
   with unchanged evidence, changed metadata/content, missing entries and changed
   baselines; changed requests never reuse the UUID/digest. Test receipt-versus-
   supersession/discard races transactionally, durable bounded evidence handoff,
   predecessor references and rejection of later old-ID submission. Replacement
   plans reuse verified existing paths; ambiguous/unrequested files are reported.
10. Cleanup/discard removes only owned workspace artifacts. Unknown files, changed
    markers, locked files or wrong roots leave data safe and report the path.
    Test every disposal-table row, including automatic cleanup of a finalized
    all-failed attempt versus retention after failed finalization, unresolved
    artifacts and an unreadable Catalog. Cleanup failure after a receipt never
    changes the committed operation result.
11. Public API documentation and a temporary-data example explain the 005.3/005.4
    division, explicit workspace placement, close-versus-discard, recovery path,
    receipt semantics, known-inventory limits and absence of copy/delete execution.

Use temporary directories and deterministic failure injection, not timing races,
network dependencies, or the user's archives. Assert bytes and relevant metadata
are unchanged for all read-only paths and failures.

### Files and architectural decisions

- New code: `src/archiver/operations.py`, `src/archiver/workspace.py`.
- Integration: `src/archiver/catalog.py`, exports in `__init__.py`, migration help
  in `cli.py`. No dependencies were added and Python/sqlite3 remain the backend.
- Tests: new operation/workspace integration suite; schema expectations updated
  in Catalog, comparison, inventory-update and duplicate-pagination regressions.
- Documentation: this outcome, parent/index, Catalog API, CLI reference, README,
  new workspace API guide and temporary-data example.
- Batches default to 1,000. Individual insertion/handoff batches cap at 10,000
  and reject oversize input; reads cap individual fetches at 10,000. These are
  storage bounds, not future copy batch-size defaults.
- The workspace persists selected observations and canonical request encoding
  before submission; fresh checks do not mutate frozen requests. Replacing an
  invalid request requires explicit fencing and a new operation UUID.
- Controller ownership is an exclusive artifact, with explicit takeover rather
  than guessed PID liveness. Close releases a lease and preserves recovery data.
- Disposal checks exact owned files and markers, never recursively removes caller
  directories, and never deletes destination content or in-root witnesses.

No implementation deviation changes the accepted domain semantics or temporary
database approach. Limits remain explicit: SQLite/storage durability and quiescent
root assumptions, unsupported future placement filesystems, caller-supplied fresh
check facts at the storage boundary, and non-atomic filesystem/database effects.
The synthetic database hook is intentionally batch-materialized for this child;
large-manifest successful-entry ingestion belongs to 005.4. Actual placement,
capability checks, production collision/replacement construction, fresh hashing
and physical deduplication are not claimed as implemented. No unresolved design
question blocks this child's storage/contract scope.
